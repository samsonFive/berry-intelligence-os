# Technical Architecture

## Architecture style

Local-first, file-backed web application with a generated read-only publication layer.

## Authoritative data

Versioned JSON files are authoritative. SQLite or another local database may later be used as a generated index, but it must be rebuildable and never become the only source of truth.

## Initial stack

- Python 3.12+
- FastAPI
- Jinja templates
- vanilla JavaScript for V1 interactions
- JSON Schema validation
- optional SQLite FTS index in a later milestone
- Git for history and distribution

## Runtime modes

### Authoring mode

Runs locally and permits intake, review, editing, validation, and publication.

### Read-only mode

Serves only published records and generated pages.

### Static-build mode

Generates deployable HTML and assets from published JSON.

## Trust boundaries

- `inbox/` or draft records are untrusted.
- `data/` published records are trusted.
- generated indexes and pages are derived.
- future web submissions must never write directly into trusted published data.

## Initial API boundaries

- `GET /api/feed`
- `GET /api/evidence/{id}`
- `GET /api/entities/{type}/{id}`
- `GET /api/search`
- `POST /api/intake` — local authoring mode only
- `POST /api/review/{id}/publish` — local authoring mode only

## Page routes (Milestone 1)

- `GET /` — newsfeed, accepts `q`, `berry`, `source`, `priority` (`dimension:level`) query params combined with AND logic.
- `GET /evidence/{id}` — evidence detail page.
- `GET /entities/{entity_type}` — listing page for one entity type.
- `GET /entities/{entity_type}/{entity_id}` — entity detail page. A single template renders every entity type (company, variety, retailer, etc.) so no entity type is privileged in the UI layer, consistent with ADR-0004.

## Intake and the inbox (Milestone 2)

- Draft evidence created through intake is written to `inbox/evidence/{id}.json` and uploaded attachments to `inbox/attachments/{id}/`, not into `data/`. This makes the untrusted/trusted boundary a physical directory split rather than only a `status` field, matching the trust-boundary rule above and the capture flow described in `README.md`.
- Draft records reuse the evidence `id` shape (`ev-<timestamp>-<slug>`) but are not required to satisfy `evidence.schema.json` (in particular `priority` is `null` until reviewer assignment in Milestone 3). `scripts/validate_records.py` intentionally does not scan `inbox/`.
- The HTML intake form posts to `POST /intake` (not `/api/intake`) because it is a multipart form submission that redirects back to a rendered page (POST/redirect/GET), not a JSON API call. `POST /api/intake` remains reserved for a future programmatic/JSON intake path with the same underlying write logic.
- `GET /intake`, `GET /intake/{id}`, and `GET /intake/{id}/attachments/{filename}` render the intake form and let a submitter review what was captured, including original attachments — satisfying "original submission is preserved" without yet building the Milestone 3 review/structure workspace.
- Write endpoints check `AUTHORING_MODE` (from the `BIOS_MODE` environment variable, default `authoring`) and return `403` when not in authoring mode, giving the "Runtime modes" section above a concrete enforcement point.

## Review, structure, and publish (Milestone 3)

- `schemas/fact.schema.json` and `schemas/relationship.schema.json` were added; `scripts/validate_records.py` now also validates `data/facts` and `data/relationships`. Every fact requires `reviewer`, `confidence`, `status`, `created_at`, and at least one `evidence_ids` entry, matching the PRD's trust requirements (section 9). Every relationship requires at least one `evidence_ids` entry.
- `GET /review` and `GET /review/{draft_id}` render the split-pane review workspace (original submission vs. proposed structured record); `POST /review/{draft_id}/publish` performs entity match-or-create, writes proposed facts and relationships, and publishes the evidence record — all gated by `evidence.schema.json` validation before anything is written, so a failed publish leaves no orphaned entity/fact/relationship files. Like `/intake`, this is a form endpoint under `/review/...` rather than `/api/review/{id}/publish`, for the same POST/redirect/GET reason noted above; `/api/review/{id}/publish` remains reserved for a future JSON path.
- The published evidence keeps the same `id` it was assigned at intake (`ev-...`); fact and relationship ids are derived from it (`fact-<suffix>-N`, `rel-<suffix>-N`). Draft ids now include a short random suffix (`ev-<timestamp>-<random>-<slug>`) so two same-title submissions in the same second can't collide.
- Entity matching is by case-insensitive exact name + entity type against `data/entities/`. No match creates a new entity with `status: unverified` — a reviewer upgrades its status later; this is the "entity matching and creation" behavior, not fuzzy/AI matching (that is Milestone 6).
- Every proposed fact for one evidence item is linked to every entity the reviewer attached to that item (there is no per-fact entity picker in this v1 form); relationships must reference two of those same linked entity names.
- Duplicate detection (`find_possible_duplicates`) is a normalized-title exact/substring match against both published evidence and other pending drafts — intentionally simple and disclosed as such, not semantic similarity.
- Publishing moves any intake attachments from `inbox/attachments/{draft_id}/` to `data/attachments/{evidence_id}/`, served at `GET /evidence/{id}/attachments/{filename}`, so uploaded files survive the untrusted → trusted transition instead of being orphaned when the draft is deleted.
- New entity folders under `data/entities/` follow the existing irregular-plural convention (`company` → `companies`, `variety` → `varieties`, `geography` → `geographies`, `person` → `people`, `berry` → `berries`), defaulting to `+s` otherwise.

## Analyst workflow (Milestone 4)

- `schemas/strategic-question.schema.json` and `schemas/signal.schema.json` were added; `scripts/validate_records.py` now also validates `data/strategic-questions` and `data/signals`. A signal requires `evidence_ids` (at least one) so every signal keeps the "Published lineage" chain (`DOMAIN-MODEL.md`) traceable back to evidence, even when it is also supported by facts.
- `GET /work-queue` is the PRD's "Home / analyst cockpit" module (new evidence, drafts awaiting review, unresolved entity matches, high-priority items, recent signals) — deliberately kept separate from `GET /` (Newsfeed), since the PRD lists them as two distinct primary modules.
- `GET /queues/{dimension}` (`reading`/`testing`/`commercial_position`/`monitoring`) replaces the Milestone 1 `/?priority=dim:high` filter shortcut with a dedicated table view. A queue includes any item at `low`/`medium`/`high` for that dimension (not `high` only), sorted highest-priority-first and newest-first within a level, so the sidebar counts reflect everything needing attention rather than only the most urgent slice.
- Strategic questions are read/link-only in this milestone (`GET /strategic-questions`, `GET /strategic-questions/{id}`) — creating or editing one is out of scope; they're currently seeded like other sample data and linked to evidence during `/review/.../publish`.
- Signals are analyst-authored, not evidence-derived like facts/relationships: `GET /signals/new` and `POST /signals` let a reviewer cite existing published evidence/fact/entity ids directly (validated to exist) rather than reusing the intake→review pipeline, because a signal is a cross-cutting pattern observed *after* evidence exists, not something produced while reviewing one evidence item. AI-assisted signal clustering remains Milestone 6.
- `POST /signals` is gated by `AUTHORING_MODE` like the other write endpoints.

## Static publication (Milestone 5)

See `docs/07-static-deployment/STATIC-DEPLOYMENT.md` for the full deployment guide. Key decisions:

- `scripts/build_static.py` renders the same Jinja templates the live app uses (imported directly from `app.main`, not duplicated) into `generated/`, reading only `data/` — it never opens `inbox/`. This keeps the static build reproducible from, and only from, trusted records, and guarantees the live and static views can't visually drift apart.
- Every internal link is rewritten to be relative to the file containing it (depth computed per output file), rather than using a single configured `<base href>` prefix. This makes the output deployable at any host and any subpath with zero build-time configuration — no `--base-path` flag to get wrong.
- A new `static_build` template flag (default falsy, so it never affects the live app unless a route explicitly sets it) suppresses UI that can't function without a server: the global search box and the newsfeed's filter form. Shipping a form that silently does nothing on a static host was judged worse than omitting it with an explanatory note.
- The already-existing `authoring_mode` flag (previously only passed by some routes) is now passed consistently by every page-rendering route, so the "Review Queue" nav item — meaningless without a write-capable backend — is correctly hidden whenever a page is rendered with `authoring_mode=False`, in both the read-only live mode and the static build.
- Draft-exclusion is enforced twice: structurally (the generator's data access only touches `published_evidence()` / `all_entities()` / etc., which read `data/`, never `inbox/`) and by an explicit post-build scan (`validate_no_drafts_leaked()`) that greps every generated HTML file for any id or title belonging to a still-unpublished draft and fails the build if one is found. `tests/test_build_static.py` exercises both the happy path and a deliberately-forced leak to confirm the scan actually catches violations.

## Filter completeness fix

The PRD's V1 success criteria (section 10) require filtering by "berry, competitor, source, geography, event type, and priority." Competitor and geography filtering did not exist through Milestone 5 — geography wasn't even a field on evidence. Fixed:

- `evidence.schema.json` gained an optional `geography_ids` array (backward compatible; existing records without it remain valid). Geography is modeled as an entity (`entity_type: "geography"`), consistent with how companies/varieties/retailers already work, rather than a free-text field — this makes geography pages, entity matching, and relationship linking fall out of the existing entity infrastructure for free.
- The review/publish workflow gained a "Geographies" field alongside Companies/Varieties/Retailers, using the same match-or-create logic; `geography_ids` on the published record is derived as the subset of `entity_ids` whose entity is type `geography`, so no separate linking step was needed.
- The newsfeed gained Competitor and Geography filter dropdowns. "Competitor" filters by `entity_ids` restricted to `entity_type: "company"` in `filter_options()` — the underlying `filter_evidence(entity=...)` support was actually one line, since entity linking already existed; what was missing was the UI and the options list.
- "Event type" from the same PRD sentence remains unimplemented: there is no `event_type` field anywhere in the data model, and no evidence in the sample data suggests one — adding it now would mean designing a new taxonomy with nothing to validate it against, which is a decision better made against real captured data.

## Automated source monitoring

The PRD's Deferred list (section 5) explicitly excludes "automatic web scraping" and "real-time alerts" from V1. This feature reopens that decision at the user's explicit request, with a scope narrower than either: RSS/Atom polling only (no general scraping), and evidence lands as `published` immediately rather than through the review queue — a deliberate deviation from "AI proposes, human approves" (WELCOME.md principle 5) for this one ingestion path, chosen and confirmed directly by the user after being shown the review-queue alternative. Mitigated by making auto-captured items visually distinct and one-click reversible rather than indistinguishable from reviewed evidence.

- `data/configuration/sources.json` holds user-managed sources (`type: "rss"` or `"keyword"`, plus label/value/enabled). A keyword source has no separate search backend — it's rewritten to a Google News RSS query URL (`google_news_rss_url()`) at fetch time, so both source types share one fetch path (`fetch_source_entries()` → `feedparser.parse()`).
- A background `asyncio` task (`source_polling_loop()`, started from the FastAPI `lifespan` context manager) checks all enabled sources every 15 minutes, offloading the blocking `httpx`/`feedparser` work via `asyncio.to_thread` so a slow feed can't stall the event loop. The task is guarded by `"pytest" not in sys.modules` — it must never make real network calls during a test run; tests instead call `check_source()`/`check_all_sources()` directly with `httpx.get` monkeypatched.
- Dedup is by `source_url`, checked against every existing evidence record (`existing_evidence_source_urls()`) — not a per-source seen-list — so a URL already captured any other way (manual intake, bulk import, another source) is never re-created.
- **`SOURCE_MAX_NEW_ITEMS_PER_CHECK = 20`**: found by actually running a live keyword source against real Google News RSS during verification, which wrote 100 items in one check. Uncapped, the very first check of any reasonably broad source floods the feed. Items past the cap aren't lost — they're still "new" (not yet in `existing_evidence_source_urls()`) and get picked up on a later cycle, so a large backlog trickles in over several checks instead of arriving as one flood.
- Auto-captured evidence carries `auto_captured: true` and `validated: false` (both new optional `evidence.schema.json` fields, backward compatible). Every card/detail page for such a record shows an "AUTO-CAPTURED — UNVALIDATED" banner with one-click **Validate** (`POST /evidence/{id}/validate`, sets `validated: true`) and **Purge** (`POST /evidence/{id}/purge`, hard-deletes the file) actions. Purge refuses to run on any record where `auto_captured` isn't true, so it can't be used to silently remove manually-authored or imported evidence.
- New dependencies: `feedparser` (RSS/Atom parsing) and `httpx` (the fetch client — previously only a transitive test dependency via `TestClient`, now also used in production code, so pinned explicitly in `requirements.txt`).

## Region filtering across the app

Filtering by Region, Berry, Company, and variety name/code was requested for every list page, not just the newsfeed (which already had berry/competitor/geography). "Region" (Americas / Europe / Oceania / Middle East & Africa) didn't exist in the data model at all before this.

- `REGION_LOOKUP` is a fixed default table mapping geography name → region, confirmed with the user as "recommended default, must stay correctable." A per-geography override lives at `attributes.filter_region` — deliberately **not** `attributes.region`, because real imported geography entities already carry their own `attributes.region` in a different taxonomy (e.g. Australia: `"Asia-Pacific"`; Chile/Mexico/Peru: `"Latin America"`) for the package's own purposes. The first implementation used the obvious key name, `geography_region()` silently treated that pre-existing data as if it were a user correction, and Australia's derived region came back "Asia-Pacific" instead of "Oceania" — caught by checking a real page (`/entities/variety/variety-bonita`) after building, not by reasoning about the code. A geography not in the lookup and without an override (e.g. China) is left unclassified rather than guessed into the wrong bucket.
- Region is never stored on non-geography entities. `entity_regions()` derives it: the union of regions from every geography linked to evidence that also links the entity. A variety reported on in Portugal and Australia shows both regions automatically — there's no field to keep in sync as more evidence comes in.
- **Geography can be linked to evidence two ways**: the dedicated `geography_ids` array, or just as one of the general `entity_ids` (a geography is still an entity). The imported blueberry package predates the `geography_ids` field, so all 121 of its evidence records use only the second form — 54 of them link a geography this way with `geography_ids` empty. The first implementation of both `evidence_regions()` and the newsfeed's existing "Geography" filter checked only `geography_ids`, so region filtering initially returned almost nothing against real data (1 of 42 varieties for "Europe"). Fixed by checking both conventions everywhere geography linkage is read: `evidence_regions()`, the plain `geography` filter in `filter_evidence()`, and the geography dropdown's options in `filter_options()`. After the fix, the same query returned 12 of 42.
- "Company" filtering (on any entity-list page, not just companies) uses the actual relationship graph — `related_entity_ids()` collects every entity connected to the given one via any relationship, in either direction — rather than a weaker "appears in the same evidence record" heuristic. This was a real design choice, not the default: co-occurrence in evidence is noisier (two unrelated entities can appear in the same article), while `develops`/`owns`/`licenses`/etc. relationships already encode the actual connection for exactly this purpose.
- Variety "code" search rides the existing text-search convention (`filter_entities()`'s `q` parameter also matches `attributes.selection_code` and `attributes.patent_number`, not just name/aliases/description) rather than a separate dedicated field or endpoint.
- Scope of this pass: newsfeed and every `/entities/{type}` listing got full filtering (q/berry/region/company as applicable); priority queues got region only. Strategic questions and signals listings were deliberately left unfiltered — small, low-traffic lists (8 and typically 0-few items) — flagged as a scope cut rather than silently left incomplete.
- Found and fixed in the same pass, not filtering-related but blocking verification of it: `scripts/build_static.py` calls `base.html`'s `queue_counts()`/`pending_review_count()` Jinja globals on every single page render, and both re-read `data/` from disk uncached on every call. At the current record volume (~300+ generated pages) this made a full static build hang for minutes instead of completing. Fixed by computing both once at the top of `build()` and overriding the globals with the precomputed values for the duration of that build — safe there specifically because nothing in `data/` changes mid-build, which is not true of the live server, so the live app's routes were left as they were. The live app pays a real, now-measured ~0.3s/page cost from the same globals; not fixed here since it's outside what was asked, but worth knowing before it's mistaken for a network issue.

## Client-side search for the static build

The live app's search is server-side (`?q=` against `filter_evidence()`), which doesn't exist on a static host. The static build (`docs/07-static-deployment/STATIC-DEPLOYMENT.md` has the user-facing detail) needed its own, and the choice was between a client-side search index and a hosted search service (Elasticsearch/Algolia/Typesense/etc.).

- Went with [Pagefind](https://pagefind.app): it indexes the generated HTML at build time and ships a small JS/WASM runtime that runs the actual search in the visitor's browser — no server, no external service, no bill, no API key exposed to the browser. A real hosted search engine would give more (typo-tolerant ranking, faceting) but needs its own infrastructure and syncing step, and — more importantly for this project specifically — is exactly the kind of proprietary SaaS dependency ADR-0001 has avoided since the first milestone. At the current scale (~300 pages) a client-side index has no real downside to justify that trade.
- Installed via `pip install pagefind pagefind_bin` (a thin Python wrapper plus a separate platform-binary package), not npm — the project's toolchain stays Python-only, no Node.js requirement added. `build_search_index()` in `scripts/build_static.py` runs it as a subprocess after all pages are written; it's optional locally (skipped with a note if not installed, so the build still succeeds) and required in CI (`deploy-pages.yml` installs it explicitly, so a Pagefind failure there is a real build failure — the deployed site is expected to always have working search).
- The subprocess call needed `encoding="utf-8", errors="replace"` set explicitly. Without it, `subprocess.run(text=True)` defaults to the Windows code page (cp1252) for decoding Pagefind's UTF-8 output, which crashed a background reader thread on non-ASCII content. It didn't fail the build (Python prints an unhandled thread exception via `threading.excepthook` rather than propagating it to the caller), so this was a silent-until-noticed bug, not a crash — found by reading the build's own output, not by it visibly failing.
- Verified, not assumed, that Pagefind's generated result links work when the site is deployed at a subpath (`https://samsonfive.github.io/berry-intelligence-os/`, not domain root): served `generated/` nested one level deep locally to simulate it, searched, and confirmed result links carried the subpath prefix and navigated correctly. Pagefind resolves its own root from wherever `pagefind-ui.js` is actually loaded from — the same trick this project's own link-rewriter uses — so it required no configuration to get this right, consistent with the static build's existing "deployable at any subpath, zero configuration" property.
- `data-pagefind-body` scopes indexing to `<main>`'s content in `base.html`, wrapped around the shared `{% block content %}` rather than split across it (an initial version put the opening `<div>` inside the block and the closing `</div>` outside it, which would have orphaned the closing tag the moment any child template overrode the block — caught before ever running it, by reading the diff). Without this, every page's identical sidebar nav would be indexed on every page too, polluting results and bloating the index for no benefit.
- Pagefind's UI ships default styling; `app.css` overrides its CSS custom properties (`--pagefind-ui-*`) to match the navy/white palette rather than looking like an unstyled drop-in widget.

## Recent Activity feed and real-date backfill

The approved mockup (`assets/platform-visual-language.png`, panel 4, "ENTITY PAGES") showed a chronological "Recent Activity" timeline (Date, Headline, Type, Priority) on every entity page — never actually built across Milestones 1-5. Without it, an entity page had evidence, facts, and relationships in three separate, unsorted sections, and there was no way to answer "what's the latest development for company X," despite that being one of the platform's stated purposes (newsfeed / market monitoring).

- `entity_activity()` in `app/main.py` merges linked evidence, facts, and relationships into one list sorted newest-first, rendered as `app/templates/entity.html`'s new "Recent activity" section (`.activity-timeline` in `app.css`). `scripts/build_static.py`'s entity-page loop was updated to compute and pass the same `activity` context key, and — while doing so — was found making the same disk-read-per-loop-iteration mistake documented above for `queue_counts()`, just for `facts_for_entity()`/relationships this time (`facts_all`/`relationships_all` are now loaded once outside the loop); it was also found never computing `regions` for entity pages in the static build at all, a pre-existing gap unrelated to this feature, closed in the same pass.
- **Verifying the feature against real imported data surfaced a second, more fundamental problem than the missing feature itself**: roughly half of imported evidence (60 of 124 records — mostly reference material such as company/registry/catalog/patent pages) has no `published_date`, only a `captured_date` marking when it was pulled into the system during the blueberry-pilot import. The first version of `entity_activity()` fell back to `captured_date` when `published_date` was missing, which made evergreen reference pages display as if they happened *today* — actively worse than the missing-feature problem being fixed, since it would show a company's static "Varieties" page at the top of a "what's new" feed dated one day in the future. Fixed by dropping the `captured_date` fallback entirely: an evidence item without a real `published_date` is excluded from Recent Activity (it remains visible in the existing Linked Evidence section, just not misrepresented as recent news).
- The same root problem existed one level deeper: facts only ever had `created_at` (an authoring/review timestamp — nearly all facts were reviewed the same import day), not a real event date, even when the fact's own statement text names one (e.g. "acquired... reported 20 October 2021"). Added an optional `event_date` field to `fact.schema.json` and backfilled it across the existing 186 fact records by extracting dates from `statement` text — conservatively: only when exactly one calendar date (day-precision `D Month YYYY` / ISO, or month-precision `Month YYYY`) appears and it isn't part of a "retrieved/accessed/as of" phrase (which names when the source was checked, not when the thing happened). Statements with zero or multiple date mentions are left alone rather than guessing which one is "the" event — ambiguous multi-date statements (e.g. "granted ... on application filed ...", "listed ... and delisted ...") are common in the patent/PBR-record data and guessing wrong would be worse than the status quo fallback. This filled in 45 of 186 facts and, by the same method applied to evidence title/summary text, 6 of the 60 undated evidence records. `entity_activity()` now prefers `fact.event_date`, falling back to `created_at` only when no event date could be extracted — so the majority of facts (unextractable dates, or genuinely dateless claims like ongoing licensing arrangements) are unchanged from before, not made worse.
- A first version of the backfill script had a real bug caught during spot review, not by the tests: the month-year fallback pass didn't apply the same retrieval-context exclusion as the day-precision pass, so `"...register index as retrieved on 4 August 2026"` — correctly rejected as a retrieval date at day-precision — leaked back in as a false `event_date` of `2026-08-01` via the month-year pass matching the same "4 August 2026" substring's month/year fragment. Fixed by tracking the full-date match spans and excluding any month-year match that falls inside one, rather than re-deriving the exclusion from nearby text a second time.
- Added `us_date` (a Jinja filter registered on `templates.env.filters`, `app/main.py`) to render every *displayed* date as US-style `M/D/YYYY` (no leading zeros) at the request of the user, who found the default ISO `YYYY-MM-DD` display confusing. Storage stays ISO everywhere — sorting, comparisons, and the `<input type="date">` fields on the intake/review/signal forms are untouched, since HTML date inputs require ISO and reformatting would break editing. The filter passes non-ISO values (`None`, `"—"`, free text) through unchanged rather than raising.
- Known, accepted limitation: entity pages with many facts that have neither an extractable `event_date` nor a distinguishing real-world date still cluster at the top of the feed under today's `created_at`, ranked above genuinely older dated items only by tie-breaking on insertion order — visually correct (todayed items *are* the most recently authored) but not a "this happened most recently" signal for that subset. Resolving it further would mean either manual per-fact date entry during review or higher-effort NLP disambiguation of multi-date statements — both out of scope for this pass; the fix here specifically targeted the fabricated-recency bug (undated/ambiguous items no longer masquerade as *more* recent than they are) rather than achieving 100% event-date coverage.

## Bullet-point restructuring of prose fields

The user's next complaint after the Recent Activity feed: evidence summaries, `why_it_matters`, and fact statements all render as single dense `<p>` blocks, several sentences long, hard to scan — "wordy" and repetitive-feeling.

- Investigated before touching anything: spot-checked real imported text across evidence and facts. It isn't padded with throwaway filler words — it's dense, information-bearing prose that packs 2-4 distinct claims into one run-on paragraph with no visual separation (e.g. one evidence summary crams a brand list *and* a separate awards fact into a single sentence). There's very little to cut without deleting real content (numbers, names, dates, source attribution). The user asked for both layout and wording fixes; layout was overwhelmingly the actual problem, so that's what was built. Wording tightening was reconsidered and not done in bulk — see below.
- `as_bullets()` (`app/main.py`) splits a prose field into its sentences for bullet rendering, registered as the `as_bullets` Jinja filter, applied everywhere a summary/why_it_matters/statement/description previously rendered as one `<p>`: entity pages (Recent Activity detail, Facts, linked evidence, description), evidence detail (summary, why it matters, Facts), the newsfeed, signals, strategic questions, entity list cards, and the intake/review draft views. A field that's already a single sentence still renders as a plain `<p>`, not a one-item list — the point is restructuring genuinely dense text, not adding bullet clutter everywhere.
- The storage-preserving guarantee matters here even more than for `us_date`: this only ever changes how existing text is *split*, never rewords or drops anything, so it carries none of the evidence-alteration risk a rewrite would.
- The sentence-boundary regex (`SENTENCE_SPLIT`) required care around one real ambiguity: a period that ends an abbreviation (`Inc.`, `Ltd.`, `Pty Ltd.`) is indistinguishable from a period that ends a sentence using only local text, and the data has both cases (`"Fall Creek Farm & Nursery, Inc. was founded..."` — mid-sentence — versus `"Costa Berry International Pty Ltd. The variety is marketed..."` — a genuine sentence break right after the same abbreviation). Rather than hand-maintaining an abbreviation exception list, the rule requires the character immediately before the `.`/`!`/`?` to be lowercase, a digit, or `)` — which happens to reject exactly the case a naive "period before a capital letter" splitter gets wrong: a person's middle initial (`"David M. Brazelton"` would otherwise wrongly break into `"...David M."` / `"Brazelton..."`). Verified against every stored `summary`/`why_it_matters`/`statement` (public + imported data): 241 fields produce 2+ sentences, zero produced a lowercase-starting fragment (the signature of a bad mid-sentence split).
- One genuinely repeated-verbatim block was found during the investigation (seven `fact-fallcreek-catalog-*` records each ending in the identical caveat sentence, "No storage temperature, packaging specification or quality threshold accompanies the storage figure, and no independent measurement of it was located."). Left as-is: it isn't wasted filler within any single fact — each occurrence is legitimately attached to its own variety-specific claim — and now that each fact renders as two bullets, the repetition also reads far less redundant, since it's a distinct scannable line rather than a clause folded into a wall of text. Turning it into a genuinely shared, non-repeated caveat would mean a data-model change (a separate structured field rather than sentence text), which is a bigger, separate decision, not a copyedit.

## Typo tolerance in the live app's search

The user hit this directly: searching "hortifruit" or "hortifrit" (both misspellings of the real company "Hortifrut") returned nothing on the live/local app, while the same misspelled queries against the deployed static build worked, because Pagefind (see above) has its own fuzzy matching built in and the live app's server-side search never did — `filter_evidence`/`filter_entities`/`api_search` all did a single `needle in haystack` substring check.

- `text_matches()` (`app/main.py`) is now the shared matcher for all three: exact substring first (fast path, so existing phrase-search behavior like `"example blue"` is unchanged), falling back to per-word matching where each query word must appear as a substring *or* fuzzy-match a haystack word via `difflib.get_close_matches` (cutoff 0.82) if it doesn't. Words under 4 characters are excluded from the fuzzy fallback entirely — short strings produce too many unrelated near-hits to be useful (`"cost"` scores 0.89 similarity against `"costa"` despite not being a typo of it).
- Incidental improvement from the same change: multi-word queries no longer require the words to be contiguous in the source text. Previously `"hortifrut acqui"` matched nothing unless that exact phrase appeared verbatim; now each word is checked independently, so it matches text like "Hortifrut acquired...". This was a side effect of restructuring the matcher, not a separate feature, but is a strict improvement — every query that matched before still matches (fast path preserved), and some now-reasonable queries that matched nothing before now do.
- This only touches the live app. The static build's search was already typo-tolerant via Pagefind and needed no change here.

## Auto-capture safety: opt-in polling, and a transparent (not black-box) quality signal

Seeding ~40 keyword sources and then restarting the dev server twice while iterating on templates produced over 1000 auto-captured evidence records in minutes -- `source_polling_loop()` fires an immediate check as soon as it starts, and it was starting on every authoring-mode process launch, dev iteration included, not just real deployments. Sampling the captured content afterward showed it was mostly genuinely on-topic (real trade press, USDA data, university extension pages) with some real noise from broader keywords (aggregator/listicle sites, off-taxonomy berries like goji) -- not something to reflexively delete, but not something that should silently happen on every dev restart either.

- `SOURCE_POLLING_ENABLED` (env var `ENABLE_SOURCE_POLLING`, off by default) now gates whether `source_polling_loop()` starts at all. A plain local restart during feature iteration never triggers a live poll again; a real deployment that wants monitoring sets the flag explicitly. The Sources page shows a banner explaining this and how to check a source manually (`Check now`) when polling is off.
- Considered building a trained relevance model to auto-filter capture quality; rejected as inconsistent with how every other part of this platform works -- plain JSON files, no black-box scoring, everything a human can open and read. Built instead: `bump_source_tally()` increments a `validated_count`/`purged_count` on the originating source every time a human clicks Validate or Purge on one of its auto-captured items (linked via a new `source_id` field on auto-captured evidence -- previously only a free-text label, not a stable id, was recorded). The tally is visible directly on each source's card on the Sources page: a transparent, auditable signal built entirely out of actual reviewer decisions, not a score nobody can inspect.
- Purge gained a second action, "Purge & block this domain" (`data/configuration/blocked_domains.json`, matched via `domain_of()` against each entry's link before it's ever written): a purge decision can optionally teach the poller to stop capturing from that domain going forward, checked in `check_source()` alongside the existing seen-URL dedup. Blocked domains are listed and removable from the Sources page.
- The 1000+ records from the accidental burst were kept, not purged, at the user's explicit call -- they're mostly genuinely on-topic and are the first real dataset to review with the tally/blocklist tools above. Consequence worth flagging for whoever picks up performance work next: `all_evidence()`/`published_evidence()` re-read every file from disk on every call, uncached (same class of issue as the `queue_counts()` and `facts_for_entity()` fixes documented elsewhere in this file). At ~1500 evidence records this now measures 0.6-1.1s *per call*, and most routes call one of them more than once per request -- the full test suite went from ~30s to ~6 minutes over the course of this session purely from data volume, no test logic changed. Not fixed here (out of scope for a documentation feature), but no longer a hypothetical either.

## Performance: caching load_json_files(), and why it's safe

The 1500+-record auto-capture backlog (previous section) made the measured cost concrete: 0.6-1.1s per `all_evidence()`/`published_evidence()` call, most routes calling one more than once, the full test suite going from ~30s to over 6 minutes purely from data volume. Fixed at the root: `load_json_files()` (the function every `all_*()` accessor funnels through) now caches its folder scan against a signature of `(filename, mtime_ns)` for every file currently in that folder, recomputed on every call.

- Correct by construction rather than by remembering to invalidate: the signature is derived from the filesystem's actual current state, not from tracking which code paths wrote something. Any write -- `save_evidence()`, a route's direct `path.write_text()`, even a file edited outside the app entirely -- changes that file's mtime (or the folder's file list, for adds/deletes), so the very next call sees a different signature and re-reads. There's no dirty flag to forget to set, which matters here specifically because writes to `data/evidence` happen from several different call sites (`save_evidence()`, `evidence_validate()`, `evidence_purge()`, the review-decision script), not one central place.
- Confirmed no caller mutates a record dict in place and expects that mutation to be invisible elsewhere -- every write path in this codebase re-reads from disk, mutates its own local copy, and writes back, rather than mutating an object obtained from `all_evidence()`/`all_entities()` -- so returning the same cached list objects across calls (rather than deep-copying per call) is safe.
- A stat() per file is still O(n) in the file count, same as the read it replaces, but a stat is microseconds against milliseconds for a full read+`json.loads()` -- roughly a 100-1000x speedup for the overwhelmingly common case where nothing changed between two calls in the same request. Measured: cold call 0.34s, cached call 0.044s at ~1700 records; full test suite 373s -> 57s.
- Test isolation (`_isolate()` swapping `main.DATA_DIR` to a fresh `tmp_path` per test) is unaffected: the cache is keyed by the folder `Path` itself, and every test gets a distinct path, so cache entries never collide across tests -- they just accumulate harmlessly in memory for the life of the pytest process.

## Fixing the domain the "block" feature actually needs

Sampling the auto-capture backlog for the review spreadsheet (next section) surfaced a real bug in the block-domain feature added earlier the same session: every keyword-captured record's `source_url` is a Google News redirect (`news.google.com/rss/articles/...`), never the actual publisher -- confirmed the redirect doesn't resolve via a normal HTTP follow (`httpx` with `follow_redirects=True` stays on `news.google.com`; Google News uses client-side JS redirection, not a 3xx). That meant `domain_of(source_url)` was always `news.google.com`, so "Purge & block this domain" was blocking the wrong thing -- and worse, doing so even once would have silently disabled every keyword source at once, since they all share that same wrapper host.

- Google News RSS entries carry the real outlet in `entry.source.{href,title}` (confirmed against a live fetch), which `feedparser` already exposes and which `build_auto_evidence()` wasn't reading. Now it does: `source_name` is the real publisher (`"FreshPlaza"`) instead of the internal monitoring-source label (`"Netherlands berry greenhouse"`) that was there before, and a new `origin_domain` field holds the real domain for blocking. Plain RSS feed entries have no `.source` (the feed already *is* the publisher), so they're unaffected.
- Added `UNBLOCKABLE_DOMAINS = {"news.google.com"}` and centralized every write to the blocklist through `add_blocked_domain()`, the only function allowed to touch it, specifically so a future call site can't reintroduce this bug by forgetting to check. It silently no-ops rather than blocking the redirect host.
- The 1585 already-captured records predate this fix and have no real `origin_domain` to backfill -- resolving it after the fact isn't possible without a JS-executing browser per link (confirmed above), and guessing a domain from the publisher name would be exactly the kind of fabrication this project avoids for dates and everywhere else. Left unset; those specific records simply can't be blocked by domain until a future capture from the same outlet exists with the field populated. `source_name` *was* safely recoverable for them without fabrication -- Google News titles are consistently formatted `"<headline> - <Publisher>"` (confirmed against all 1585 stored titles, 0 missing the separator; 25/25 randomly sampled tails were clean, plausible outlet names) -- so a one-off backfill fixed the misleading label on every existing record.

## Reviewing a 1500-record backlog outside the web UI

Reviewing 1585 unvalidated records one at a time through the newsfeed's Validate/Purge buttons isn't practical. `scripts/export_for_review.py` exports the full `auto_captured and not validated` backlog to an `.xlsx` (via `openpyxl`, new dependency) with a `decision` column (data-validated dropdown: `validate` / `purge` / `purge+block`) plus publisher, real domain, originating keyword, date, summary, and source link -- sorted by domain first so items from the same noisy or valuable outlet cluster together for fast bulk decisions. `scripts/apply_review_decisions.py` reads the same file back and applies every non-blank decision: validate sets `validated: true` and credits the source's tally, purge deletes the record and debits it, `purge+block` also calls `add_blocked_domain()`. Both scripts import `app.main` for the same underlying logic the web routes use (`bump_source_tally`, `add_blocked_domain`, ...) rather than duplicating it. `review/` (the working spreadsheets) is gitignored -- transient review state, not source-controlled data, same treatment as `generated/`.

## Search: bounded dropdown, real results page, cleaner excerpts

The deployed site's search (Pagefind) had three real usability problems, all reproduced live before touching anything: the results dropdown had no height cap, so a broad query grew it past the viewport and scrolled the search box itself out of view; there was no way to see a full result set or link to one, only whatever fit in the shrunken dropdown; and excerpts on entity/evidence pages were garbled ("SourceHortifrut S.A. - `.pagefind-ui__drawer` is now `position:absolute` with `max-height:min(65vh,540px)` and its own `overflow-y:auto`, so it floats over the page and scrolls internally instead of pushing page content down. Pagefind's own CSS leaves it in normal document flow, which is what caused the original bug.
- Added `data-pagefind-ignore` to every metadata `<dl>` (entity/evidence/signal/strategic-question detail pages) and to the activity-timeline's badge/date elements on entity pages, so excerpts pull from real prose instead of concatenated labels. Verified the `<dl>` fix directly (the exact garbled string no longer appears anywhere in the rebuilt index); the activity-timeline badges turned out to be a deeper Pagefind excerpt-generation behavior that the ignore attribute didn't fully suppress in every case -- noted as a known, lower-priority residual rather than claimed fixed, since further chasing it didn't have a clear payoff proportional to the effort.
- New `app/templates/search.html`, written to `/search/` by `build_static.py`, is a real results page using Pagefind's low-level JS API (`pagefind.search()`/`.data()`) rather than the `PagefindUI` widget, styled with this site's own card layout instead of the dropdown's. Supports deep-linking via `?q=`, debounced live re-search as you type, and a "Load more" button that paginates 15 results at a time (results are already fetched as lightweight refs by `search()`; `.data()` is only called for the batch about to render). Subpath-safety (this site deploys under `/berry-intelligence-os/`) is handled the same way as everywhere else in this codebase: a `<link href="/pagefind/pagefind.js">` tag gets rewritten to the correct relative path by the existing build-time link rewriter, then the page reads that element's resolved `.href` at runtime and dynamically `import()`s it -- reusing the proven mechanism rather than reimplementing depth math in JS.
- The header dropdown's Enter key now navigates to this page instead of doing nothing useful with a shrunken result list. Getting this right needed the capture phase plus both `preventDefault()` and `stopPropagation()`: PagefindUI's `<input>` lives inside PagefindUI's own `<form>`, and without taking control before Pagefind's own handling runs, a real Enter keypress's native form submission reloads the page before this handler's navigation takes effect -- invisible when testing with a JS-dispatched synthetic event (which doesn't trigger native form submission at all), only caught testing with an actual keypress.

A `key !== "Enter"` check (the standard, correct way to detect Enter in a real browser) will never match it. ## Search result prioritization

The user searched "MBO" (an alias of "Mountain Blue Orchards") on the deployed site and found the company's own entity page ranked 7th, well behind two news articles that only mention "MBO" in passing. Reproduced live before changing anything, using Pagefind's low-level API to dump the actual ranked order rather than guessing from the UI.

- Root cause was a regression from the earlier excerpt-garbling fix in the same session: `data-pagefind-ignore` had been applied to entity pages' entire metadata `<dl>`, which includes the Aliases row -- so "MBO" wasn't in the search index for that page at all. The #7 ranking it still achieved came entirely from incidental mentions in linked-evidence titles shown on the page, not from any match on its own identity. Confirmed via Pagefind's docs (fetched directly, not assumed) that `data-pagefind-ignore` excludes the element from indexing outright, not just from excerpt display.
- Fixed by pulling Aliases out of the ignored block into its own line under the page `<h1>` ("Also known as: ..."), indexed and given `data-pagefind-weight="10"` (Pagefind's max; weighting is quadratic, so this is roughly 100x a default-weight match) -- an exact alias match is about as strong a relevance signal as this kind of search can produce, and should be treated that way. This is also a genuine UI improvement independent of search: alternate names now show near the title rather than buried in a metadata table.
- Weighting the alias alone only moved the entity page from #7 to #6, which pointed at a second, separate cause: `<h3>` is auto-weighted by Pagefind (headings get built-in boosts, h3 = weight 5, ~25x), and entity/signal/strategic-question pages render every linked evidence item's title as an `<h3>`. Any page that merely links the same evidence record -- Twilight, Chile, Naturipe Farms, none of which are "MBO" -- got the same heading-strength boost for text that isn't actually about that page's own subject. Added `data-pagefind-weight="1"` (cancels Pagefind's automatic heading boost, back to plain body-text weight) to those three templates' linked-evidence `<h3>` elements, since they're secondary references to evidence hosted elsewhere, not primary heading content of the page they appear on. This is the fix that mattered: #6 -> #3, now ranking above every page that only mentions "MBO" incidentally, behind only the two articles whose own headlines are genuinely about it.
- Stopped at #3 deliberately rather than continuing to push for #1: the two results still ahead are legitimately, directly on-topic (their headlines literally say "MBO"), and further weight tuning risks overfitting to this one query at the expense of others. Search relevance is an ongoing tuning problem, not a one-time fix -- documented here so the next iteration has the actual mechanism (`data-pagefind-weight`, quadratic scaling, automatic heading boosts h1=7/h2=6/h3=5/h4=4/h5=3/h6=2) rather than starting from scratch.

That "#3" result was still two on-topic news articles about MBO ranking ahead of MBO's own entity page -- the very next ask was to close that remaining gap and, separately, to make the newsfeed articles among the results order by recency rather than raw term-match score. A single relevance score can't express "an entity's own page always outranks any article that merely mentions it" -- that's an ordering rule, not a weighting adjustment, and no amount of per-element weight tuning reliably produces it for every query.

- Solved by moving from weight-tuning to structural filtering. Entity pages got `data-pagefind-filter="type:entity"` and evidence (newsfeed article) pages got `data-pagefind-filter="type:evidence"` plus `data-pagefind-sort="date:{{ published_date or captured_date }}"` (an inline static value, so it works even though the date itself lives inside a `data-pagefind-ignore` block -- filters and sort tags apply regardless of `data-pagefind-ignore`, confirmed via Pagefind's docs). `published_date` is preferred over `captured_date` since it's when the article actually ran, not when this app happened to capture it.
- `search.html` now runs three Pagefind queries per search term in parallel and merges by result id, keeping first-seen order: `filters:{type:"entity"}` (Pagefind's normal relevance ranking -- this is what puts the actual subject of the query at the top, on top of the alias/heading weighting already in place), then `filters:{type:"evidence"}, sort:{date:"desc"}` (newest first), then a plain unfiltered query as the authoritative fallback so nothing is ever dropped -- anything not already surfaced by the first two (signals, strategic questions, listing pages) still appears, in normal relevance order, after them. Confirmed live: searching "MBO" now puts Mountain Blue Orchards' own page first, and the two genuine MBO news articles (30 Jul 2026 and 2020) both appear ahead of unrelated content and correctly ordered newest-first relative to each other.
- Deliberate scope decision: entity pages now rank above evidence pages for any query that matches both, not just company-name queries -- there's no cheap way to detect "this query is a company/competitor name" ahead of running the search. Accepted as reasonable for this product specifically: entity/competitor profiles are the core object type users are looking for, so biasing toward them isn't a mistuning the way it would be for a general-purpose search engine.
- This only reorders the dedicated `/search/` results page, not the header dropdown preview (`PagefindUI` in `base.html`) -- that's a prebuilt widget that doesn't expose per-bucket filter+sort merging, and the dropdown is already documented as a quick preview whose Enter key sends you to the full results page for anything more than a glance.

## Resolving real article summaries for auto-captured evidence

`is_redundant_summary()` (see "Making the newsfeed actually useful" above) correctly detects and hides the fake "summary" on Google News-sourced records, but that left the underlying problem unsolved: ~99% of auto-captured evidence (1129 of 1139 validated records) showed "No summary available from this source -- read the full article" instead of any real content, because Google News search results never provide a genuine excerpt in the first place.

- **Why a plain HTTP client can't fix this.** Google News RSS `<link>` values are wrapper URLs (`news.google.com/rss/articles/...`) that redirect to the real article via client-side JavaScript, not an HTTP 3xx -- confirmed directly with `httpx.get(url, follow_redirects=True)`, which stays on `news.google.com`. A real browser executing that JS resolves it correctly, confirmed both with this session's own browser tool and with Playwright, before committing to building anything around it.
- **`scripts/resolve_real_summaries.py`** uses headless Playwright (Chromium) to visit each candidate's `source_url`, let Google's redirect run, and pull the publisher's own `<meta property="og:description">` (falling back to `<meta name="description">`, then the first substantial `<p>` on the page) -- real text the publisher wrote about their own article, not a paraphrase generated here. Each record is written back to disk immediately on success, so a stopped run never loses progress; reruns naturally skip anything already resolved via the same `is_redundant_summary()` check used to find candidates.
- **Wait strategy**: `wait_until="networkidle"` (no network activity for 500ms) measured a ~33% timeout rate on real news sites, which never go fully idle within any reasonable timeout thanks to continuous ad/analytics polling -- pages that had, in fact, loaded fine. Switched to `wait_until="commit"` (waits only for navigation to start) paired with an explicit `page.wait_for_url(...)` for the redirect and `page.wait_for_load_state("domcontentloaded", ...)` for the landing page, which measured 88-91% success with zero timeouts.
- **Block detection is retry-then-skip, not stop-on-first-sight.** A run hit what looked like a block (title/body matching known Google/Cloudflare block phrasing) mid-batch; the same URL loaded clean seconds later via a fresh call, showing it was a transient "checking your browser" interstitial, not a real block -- fixed with a sleep-and-reload retry before treating anything as blocked. A later run hit a second block at the same domain, this time with a visible Cloudflare challenge token in the URL -- a genuine, persistent, site-specific block. Halting the entire run over one stubborn site would have sacrificed hundreds of other good records, so the policy is skip-and-continue on a confirmed block, with a sliding window (3+ blocks within any 20-record span) as the actual "stop the run" signal, since that pattern would mean something systemic (e.g. this IP being rate-limited) rather than one site's own protection.
- **Crash recovery is two-layered.** A mid-run `Target crashed` error (the Chromium tab itself dying, unrelated to blocking) surfaced outside the original narrow try/except -- it wrapped only the navigation calls, not the later `page.locator("body").inner_text()` call where the crash actually appeared -- and took down the whole process. Fixed by wrapping the entire per-record body (navigation through save) in one broad `except Exception`. A subsequent run then hit a case where the recovery itself (`browser.new_page(...)`) failed with a connection-closed error, meaning the whole browser process had died, not just the tab -- fixed with a nested try/except that relaunches the entire browser if page recreation fails.
- **Result**: 1039 of 1139 validated records (91%) now have real, publisher-written summaries, plus a bonus fix -- `origin_domain` is now correctly populated for all of them (previously only set for RSS-sourced records), which retroactively makes the domain-block feature work for these too. The remaining 100 genuinely lack an extractable meta description on their specific pages -- a content ceiling, not a script limitation.

## Rebuild guarantee

Deleting `generated/` must not destroy knowledge. Running a rebuild command must recreate indexes and published pages from schemas, configuration, and trusted data.
