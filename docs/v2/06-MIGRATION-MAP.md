# Intelligence OS — Migration Map (V2)

**Status:** Planning draft, not accepted.

## Ground rules

- **No big-bang rewrite.** Every `REPLACE` below has a migration bridge — a way for the old and new to coexist during transition, verified working before the old path is retired.
- **The V1 application keeps running throughout** (Core Design Principle #10) — nothing in this map requires taking Berry Intelligence OS offline to migrate it.
- **The V1 baseline is tagged and frozen** (Phase 0, `07-IMPLEMENTATION-ROADMAP.md`) before any of this begins, so it remains a recoverable reference regardless of how migration proceeds.

## Disposition key

- **KEEP** — used as-is in V2, no change needed.
- **ADAPT** — the underlying concept/asset survives, but its implementation or location changes.
- **REPLACE** — the V1 implementation is superseded by something structurally different; a migration bridge is specified.
- **NEW** — has no V1 equivalent; built fresh for V2.
- **DEFER** — a real decision or component genuinely not needed for V2's scope; explicitly named so it isn't silently dropped.

## Inventory

| Component | Disposition | Detail |
|---|---|---|
| **JSON Schemas** (`schemas/*.schema.json`) | **ADAPT** | Extended, not replaced — every V2 Postgres table maps to (and validates against) an evolved version of these same schemas (new fields: `relationship.confidence`, `evidence.source_tier`/`event_date`, new `assessment.schema.json`/`recommendation.schema.json`). The schemas remain the authoritative shape definition even after Postgres becomes the operational store (Core Design Principle #8) — Postgres columns are generated *from* the schema, not the other way around. |
| **JSON file storage** (`data/*/`) | **REPLACE** | Superseded by PostgreSQL as the operational store (`02-TARGET-ARCHITECTURE.md` Section 3). **Migration bridge**: Phase 3 (`07-IMPLEMENTATION-ROADMAP.md`) is an explicit dual-write/parity period — the app writes to both JSON files and Postgres simultaneously, with an automated parity check (every Postgres row exports back to byte-comparable JSON) run continuously until confidence is high, before JSON-file writes are turned off. The JSON files themselves are never deleted; they become the initial seed data plus a permanent point-in-time archive. |
| **`app/main.py`** (2,512-line monolith) | **ADAPT** | Split into routers/services by concern (Section 1, `02-TARGET-ARCHITECTURE.md`) — the same routes, same behavior, reorganized. No route's external behavior changes as a result of this split; it's a structural refactor validated by the existing 122-test suite continuing to pass unmodified in intent (test *targets* may move, test *assertions* should not need to change). |
| **FastAPI** | **KEEP** | Nothing about V1's framework choice is a problem `CURRENT-STATE-AUDIT.md` identified. Stays the web/API framework for V2. |
| **Jinja2 templates** (`app/templates/*.html`) | **ADAPT** | Stay server-rendered Jinja2 (Section 1, `02-TARGET-ARCHITECTURE.md`). Adapted in two ways: (1) Domain-specific rendering choices (entity-type-specific quirks, if any survive scrutiny) move behind Domain Pack configuration rather than being hard-coded per template; (2) new templates are added for the new object types (Assessment, Recommendation, Report) and the new synthesis/rollup views that close `CURRENT-STATE-AUDIT.md`'s largest gap. Existing templates for Evidence/Entity/Fact/Relationship rendering are the starting point, not rewritten from scratch. |
| **Search — live app** (Python substring/typo-tolerant scan) | **REPLACE** | Superseded by Postgres full-text search (`02-TARGET-ARCHITECTURE.md` Section 5). **Migration bridge**: both implementations can run side by side behind a feature flag during Phase 3; cut over once Postgres search is verified to return equivalent-or-better results against a fixed set of real queries (including the "MBO" alias-ranking case this session specifically tuned for, kept as a regression check). |
| **Search — static build** (Pagefind) | **KEEP** | The static/read-only publication path is preserved unchanged (`02-TARGET-ARCHITECTURE.md` Section 5) — Pagefind remains correct for a database-less static deployment target, which V2 continues to support. |
| **`search-core.js`** (shared entity-first/date-sorted ranking module) | **KEEP** | This session's own fix (unifying the header dropdown and full results page) stays exactly as-is for the static build; the *logic* it encodes (entities rank above incidental mentions, evidence sorts by recency) is worth carrying into the new Postgres-search ranking too, as a design reference, not a code dependency. |
| **Source monitoring** (`check_source()`, RSS/keyword-search polling in `app/main.py`) | **REPLACE** | Superseded by the Collector framework (`02-TARGET-ARCHITECTURE.md` Section 7, `03-DOMAIN-MODEL.md` Collector/Collection Job). **Migration bridge**: the existing RSS and keyword-search *behaviors* become the first two Collector implementations verbatim — this is a re-homing of proven logic behind a new interface, not a rewrite of the logic itself. The 120-source registry (`data/configuration/sources.json`) migrates to `Source` rows unchanged in content. |
| **`resolve_real_summaries.py`** (Playwright-based real-summary backfill) | **ADAPT** | Its crash-recovery/circuit-breaker/retry discipline generalizes into the new background job framework's shared error-handling (`02-TARGET-ARCHITECTURE.md` Section 6) rather than being re-invented per job type. The specific Playwright-based Google-News-redirect-resolution logic remains a legitimate, narrow tool for exactly the problem it solves and is not replaced. |
| **Intake** (`/intake`, draft → `inbox/`) | **ADAPT** | Same four pathways (article/URL, note/observation, upload report, standalone fact), same "preserve the original submission" discipline — re-homed onto Postgres-backed `Evidence` records with `review_state: draft` instead of a separate `inbox/` filesystem tree. **Migration bridge**: since `inbox/` currently has 0 live drafts (`CURRENT-STATE-AUDIT.md` Section 6), there is no draft-migration problem to solve — the cutover point is simply "new drafts go to Postgres from day one of Phase 3." |
| **Review queue** (`/review`, unified this session) | **ADAPT** | The unification work done this session (one page for intake drafts + auto-captured evidence, sorted by source priority) is the *design* V2 keeps — re-implemented against Postgres queries instead of two separate `load_json_files()` scans. The `/work-queue` vs. `/review` count discrepancy this session's own change introduced (`CURRENT-STATE-AUDIT.md` Section 4) should be resolved as part of this adaptation, not carried forward. |
| **Validate/purge actions** (`/evidence/{id}/validate`, `/purge`) | **REPLACE** | The `validated` boolean (meaningful only for auto-captured evidence) is superseded by the unified Evidence review-state enum proposed in `03-DOMAIN-MODEL.md` (`draft → in_review → published`, applicable regardless of how evidence arrived). **Migration bridge**: every V1 record with `auto_captured: true, validated: true` maps to `review_state: published`; every record with `auto_captured: true, validated: false` maps to `review_state: in_review` (there are currently 0 of these — `CURRENT-STATE-AUDIT.md` Section 6 confirmed the auto-capture backlog is empty at baseline, making this mapping trivial to verify); every record with no `validated` field at all (the 124 legacy/imported records) maps to `review_state: published` (since they are, factually, already published and readable today) with a `validated_via: "legacy_no_gate"` provenance note rather than inventing a false review history. |
| **Signals** (`schemas/signal.schema.json`, `/signals` routes) | **ADAPT** | Schema refined per `03-DOMAIN-MODEL.md` (adds the `minItems: 2` evidence constraint and richer status enum the blueberry import package's own proposal specified). **The 6 unapplied signals in `data/imports/blueberry-public-pilot-2026-08-03/signals/` are a concrete, ready-made first migration case** — importable as real `Signal` rows the moment the refined schema exists, closing a gap that's been sitting unaddressed since 2026-08-04. |
| **Strategic questions** (`schemas/strategic-question.schema.json`) | **ADAPT** | Status enum tightened to `active/answered/retired` per the blueberry import package's own proposal (P-6); bidirectional linking to Evidence fixed (`CURRENT-STATE-AUDIT.md` Section 7 found it currently renders one direction only). Content (9 live questions) migrates unchanged. |
| **Static deployment** (`scripts/build_static.py`) | **KEEP** | Explicitly preserved (`02-TARGET-ARCHITECTURE.md` Section 13) — reads from Postgres instead of `data/` once Phase 3 completes, but the output (a self-contained, relocatable, disposable `generated/` directory) and its "Rebuild guarantee" stay unchanged in kind. |
| **GitHub Pages deployment** (`.github/workflows/deploy-pages.yml`) | **KEEP** | Unchanged — continues to serve the static/read-only publication, independent of whatever hosts the new live/writable V2 application. |
| **Tests** (`tests/*.py`, 122 tests) | **ADAPT** | Kept as the regression baseline throughout migration — per-route/integration-style tests continue to exercise the same routes; their fixtures move from `tmp_path` JSON-file isolation to a test-database-per-run pattern once Phase 3 lands, but the *assertions* (what a rendered page should contain, what a redirect should do) are the actual value being preserved and should not need rewriting just because storage changed underneath them. |
| **Import scripts** (`scripts/export_for_review.py`, `apply_review_decisions.py`, `data/imports/.../import_package.py`) | **REPLACE** | Superseded by the general Intelligence Package import/export mechanism (`05-INTELLIGENCE-PACKAGE-SPEC.md`). **Migration bridge**: `import_package.py`'s three-gate `--dry-run`/`--apply`/`--approve` discipline is not discarded — it's the direct design precedent the new general import path is built from, and remains the concrete reference implementation to generalize rather than a piece of throwaway code. |
| **Existing data** (162 entities, 1,263 evidence, 186 facts, 204 relationships, 9 strategic questions, 120 sources) | **KEEP**, with a required migration step | The dataset itself is preserved in full (explicit product-direction requirement: "the existing blueberry dataset must be preserved"). It becomes the seed data loaded into Postgres in Phase 3, and remains simultaneously readable as the original JSON files (nothing is deleted) and exportable as a full-fidelity Intelligence Package (`05-INTELLIGENCE-PACKAGE-SPEC.md`) for archival before migration begins. |
| **`data/imports/blueberry-public-pilot-2026-08-03/`** (the import package itself, including its markdown analysis) | **KEEP** | Not migrated *into* the operational store as a package (it already was, mostly — `CURRENT-STATE-AUDIT.md` Section 6) — kept in place as-is, as the historical record of how this dataset was built and the direct design precedent for `05-INTELLIGENCE-PACKAGE-SPEC.md` and the Collector-template/Domain-Pack seed-data mechanism. Its 6 unapplied signals and unresolved `proposed-schema-enhancements.md` items (P-8 in particular) are exactly what Phase 3/4's Assessment/Recommendation/Signal work resolves. |
| **Authentication** | **NEW** | No V1 equivalent (`02-TARGET-ARCHITECTURE.md` Section 11) — genuinely new in V2, not a migration. |
| **Organization/Workspace/Domain objects** | **NEW** | No V1 equivalent — genuinely new; V1's single implicit dataset becomes the seed content of exactly one Organization/Workspace/Domain in V2 (Phase 3), not a multi-tenant migration problem. |
| **AI provider abstraction, Collector framework, background job framework, Assessment/Recommendation schemas, report generation, Export Package, the API** | **NEW** | No V1 equivalent for any of these (confirmed directly in `CURRENT-STATE-AUDIT.md`) — all net-new V2 work, covered by Phases 4-6 of `07-IMPLEMENTATION-ROADMAP.md`. |
| **Multi-tenant isolation, SSO, billing, a second real Domain Pack in production use** | **DEFER** | Explicitly out of V2 scope (`02-TARGET-ARCHITECTURE.md` "LATER" columns, Phase 8 gated on "if still justified"). Named here so nothing is silently assumed to be in scope. |

## Summary by disposition

| Disposition | Count | What this tells us |
|---|---|---|
| KEEP | 6 | The static-publication side of V1 (build script, GitHub Pages, Pagefind, this session's search-ranking fix, FastAPI as a framework, the existing dataset) needed no change to keep working — a real vote of confidence in those specific choices. |
| ADAPT | 9 | The majority of V1's *behavior* survives, re-homed onto new infrastructure — this is the "no big-bang rewrite" principle showing up as a number, not just a stated intention. |
| REPLACE | 6 | Every replacement is a case where V1's own implementation was already flagged as a real limitation in `CURRENT-STATE-AUDIT.md` (flat-file storage, the two-search-implementation split, the `validated`/`status` dual-gate confusion, hard-coded source polling, the narrow one-off import/export scripts) — replacement is targeted at documented pain, not novelty for its own sake. |
| NEW | 8 (as grouped categories) | Concentrated almost entirely in the AI/collector/reporting/multi-user layer — exactly the parts of the original product vision (`DOMAIN-MODEL.md`'s lineage chain, Milestone 6) that were always intended but never built, not scope invented for V2. |
| DEFER | 1 (as a grouped category) | Kept small and explicit on purpose — the goal is a working, generalized platform proven on a second domain, not a fully multi-tenant SaaS product on day one. |
