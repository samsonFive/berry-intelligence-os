# Intelligence OS V2 — Phase 1.5 Prototype Findings

**Status:** Written 2026-08-13, on completion of Phase 1.5B (`docs/v2/10-BACKLOG.md` BL-026 – BL-029). Covers the whole of Phase 1.5: Phase 1.5A activated Signal/Assessment/Recommendation as real objects (BL-024/BL-025); Phase 1.5B (this task) prototyped the synthesis experience on top of them (Blueberry Landscape, Company portfolio, Variety intelligence). Required reading for Phase 2's repository-interface design (`07-IMPLEMENTATION-ROADMAP.md` Phase 1.5 acceptance criteria) — not filed away unread.

**What this document is not**: a production design spec. Per this task's own framing, Phase 1.5B is a UX/information-architecture validation pass; its job is to generate findings, not ship a finished feature. Nothing here should be read as "the way Landscape/Company/Variety views must look" — only as "here is what real data and real usage actually needed."

---

## 1. What worked

- **Zero schema changes were needed.** All three prototype views (Landscape, Company, Variety) were built entirely on the schemas Phase 1 and Phase 1.5A already shipped — `entity.schema.json`, `evidence.schema.json`, `fact.schema.json`, `relationship.schema.json`, `signal.schema.json`, `assessment.schema.json`, `recommendation.schema.json`, `strategic-question.schema.json`. This is a genuinely strong signal that the Phase 1 domain model is sound.
- **The relationship model generalizes cleanly.** `subject_id`/`object_id`/`predicate`/`evidence_ids` was enough to build one fully generic, entity-type-agnostic "Portfolio & network" section (`grouped_relationships_for_entity()`) that works identically for a company, a variety, a patent, or a breeding program, with zero per-type branching. No new relationship shape was needed.
- **The trust-badge vocabulary from Phase 1.5A scaled without new component types.** Signal/Assessment/Recommendation/Fact/Claim/Counterevidence badges, designed for the intelligence-object detail pages, dropped directly into the Landscape and entity pages with only new *colors* added (`.badge-signal` etc.), not new markup patterns.
- **`entity.attributes` (free-form, unstructured by schema) already held real, rich data nobody was rendering.** `attributes.traits[]` on variety entities — each entry carrying `trait`, `value`, `provenance`, `evidence_ids`, `asserted_by` — was populated for 26 of 42 real varieties, with `provenance` values (`owner_or_marketer_claim`, `named_trial_measurement`, `regulatory_or_registry_record`, `unresolved`) that map almost directly onto the FACT/CLAIM distinction this task asked for. The data existed since import; nothing in the UI ever surfaced it before this task. Same story for `attributes.breeding_program_id` (a real entity-id cross-reference) and `attributes.patent_number`.
- **Existing helper functions (`facts_for_entity`, `evidence_regions`, `geography_region`, `entity_regions`) were directly reusable** for the Landscape's geographic and coverage rollups — no parallel implementation was needed.

## 2. Missing query capabilities

Recorded only because the prototype actually needed them — nothing here is speculative:

1. **"Every object referencing entity X"**, across Signal/Assessment/Recommendation/Fact/Relationship at once. Today this is five separate full-table-scan functions (`signals_for_entity`, `assessments_for_entity`, `recommendations_for_entity`, `facts_for_entity`, `relationships_for_entity`), each re-reading and re-filtering the same underlying files.
2. **"Entities of type X scoped to domain/berry Y."** `landscape_entities()` does a full scan of `all_entities()` on every call, filtering by `berry_id in entity.berry_ids`.
3. **Transitive domain-scope membership for objects with no domain field of their own.** Assessment and Recommendation have no `berry_ids`/domain-scope field (see Schema gaps, below) — the Landscape had to derive "is this Assessment about blueberry?" by intersecting its `entity_ids` against the set of blueberry-scoped entity ids. This works, but it's an approximation computed at request time, not a structural guarantee.
4. **A join-and-group operation for relationships**: "this entity's relationships, with the *other* entity resolved, grouped by direction and predicate." Built once as `grouped_relationships_for_entity()`, but it's Python-side joining of two full file scans (`all_relationships()` + `entity_index()`), not a query.
5. **"Evidence relevant because something else cites it"**, not simply "newest evidence." `landscape_recent_movement()` builds a whitelist of evidence ids from every Signal/Assessment/Recommendation in scope, then filters and sorts — a pattern a repository interface should support directly rather than requiring the caller to assemble the whitelist by hand.
6. **A geography rollup**: region → {geographies, companies operating there, evidence count}, computed today by iterating all relationships and all evidence once per Landscape request and bucketing by a name-based region lookup table. No caching exists across requests.
7. **Confidence/status/dispute distributions scoped to an entity set** (the Evidence coverage & limitations section) — a `Counter`-based aggregate recomputed from scratch every time.
8. **Patent-to-variety linkage has no query path at all.** The `protects` relationship predicate exists (declared in `domain-packs/berries/relationship-predicates.json`, 0 live usage) specifically for this, but no data populates it — the Landscape/Variety views had to fall back to normalized string-matching between `variety.attributes.patent_number` (free text like `"US PP28,358"`) and a patent entity's `id`/`aliases`. This works for the 12 varieties that have a `patent_number` at all, and is honestly reported as "no match found" otherwise (never guessed) — but it's a workaround, not a real query capability.

## 3. Domain Pack findings

Every berry-specific assumption introduced in this task's code, classified per the task's own CORE / DOMAIN PACK / DEFER instruction. "Core" means the mechanism belongs in `app/main.py` regardless of domain; "Domain Pack" means the mechanism is fine in core but the *content*/*convention* it reads is Berries-specific and should eventually be declarative Domain Pack configuration (`04-DOMAIN-PACK-SPEC.md`); "Defer" means neither — it's a data-hygiene or scope decision, not a Domain Pack boundary question at all.

| Function / assumption | Classification | Why |
|---|---|---|
| `grouped_relationships_for_entity()` | **CORE** | Fully generic — reads `subject_id`/`object_id`/`predicate`, resolves the other side, labels direction. No Berries assumption anywhere. |
| `signals_for_entity`, `assessments_for_entity`, `recommendations_for_entity`, `strategic_questions_for_entity` | **CORE** | Same — follow `entity_ids`/`strategic_question_ids` fields every core schema already declares. |
| `landscape_competitive_field()` (variety/patent/brand/geography counts per company) | **DOMAIN PACK** | This *is* `04-DOMAIN-PACK-SPEC.md` Section 6's "Blueberry Landscape" report template, described in the spec but never implemented until now. A SaaS-CI pack's equivalent ("Category Landscape") would roll up different predicate/entity-type combinations entirely. |
| `landscape_variety_rollup()` | **DOMAIN PACK** | Same reasoning — a report-template-shaped function, Berries-specific in its column choices (traits, patent, breeding program). |
| `landscape_geographic_footprint()`'s mechanism (bucket → aggregate) | **CORE-shaped, DOMAIN PACK content** | The bucket-and-aggregate pattern is generic; the actual `REGION_LOOKUP` table (country name → Americas/Europe/Oceania/Middle East & Africa) is a Berries-authored 4-region taxonomy a different domain wouldn't share. |
| `variety_trait_profile()` reading `attributes.traits[]` | **DOMAIN PACK, with a CORE candidate inside it** | The specific convention (a `traits` key holding `{trait, value, provenance, evidence_ids, asserted_by, conditions}`) is Berries-specific today. But the underlying *pattern* — "an attributed value with a provenance classification distinguishing an owner/marketer claim from an independent measurement" — looks broadly reusable (a SaaS-CI pack would want the identical mechanism for vendor-published benchmark numbers vs. independently audited ones). Worth evaluating as a **generalized Core mechanism** (e.g. a real `attribute_claims` object type) in Phase 4, rather than leaving it Berries-only. |
| `variety_patent_link()`'s string-normalization matching | **DOMAIN PACK** | Patent-numbering conventions ("US PP28,358") are industry-specific; a different domain has a different identifier format or no patents at all. |
| `PRIMARY_SOURCE_TYPES` (which source types count as "primary/registry-grade" for coverage stats) | **DOMAIN PACK** | Government registries and patent records are Berries' primary-source vocabulary; a SaaS-CI pack's equivalent would be analyst-firm reports or SEC filings, a completely different set. |
| `entity.html`'s "Trait profile" / "Breeding program & IP" sections, gated on `entity.entity_type == 'variety'` | **DOMAIN PACK** | The gating mechanism (show section X only for entity type Y) is a `04-DOMAIN-PACK-SPEC.md` Section 8 visualization-config idea (per-entity-type view hints); the specific sections shown are Berries content. |
| `SEED_FIXTURE_ENTITY_IDS` / `SEED_FIXTURE_EVIDENCE_IDS` hard-coded exclusion list | **DEFER** | Not a Domain Pack question at all — see Data gaps below. This is a data-hygiene problem (no structural flag distinguishes real data from V1 demo fixtures) that exists independent of which domain is active. |
| Landscape scope label `"Berries / Blueberry / Global"` | **DEFER, explicitly** | Per this task's own instruction — a real Domain/Market/Geography scope selector is out of scope for Phase 1.5B. See Section 7 for what it would require. |

## 4. Schema gaps

- **Assessment and Recommendation have no domain/berry-scope field.** This is the one concrete, load-bearing schema gap this prototype surfaced. Every other core object that needed berry-scoping already has it (`Entity.berry_ids`, `Evidence.berry_ids`, `Signal.berry_ids`); Assessment and Recommendation don't, because `03-DOMAIN-MODEL.md` explicitly deferred "workspace/domain scoping fields" to Phase 3 (D-008). The Landscape's transitive entity-intersection workaround (Section 2, item 3) is a real approximation, not a design recommendation — Phase 2/3 should resolve this deliberately (either a direct scope field, or a repository-level computed-membership view), not by extending the workaround further.
- **No schema change was made in this task.** Per the task's own instruction, no major schema design was silently altered; the one candidate for a future minor addition — a scope field on Assessment/Recommendation — is recorded here as a finding, not implemented.
- **`entity.attributes` is fully free-form**, with no schema-level guarantee about the shape of sub-structures like `traits[]`. It happens to be populated consistently across the real variety dataset today, but nothing prevents a future import from using a different shape, which the UI would then silently fail to render (no error — just an empty trait profile). Not fixed here (would be a schema change); flagged for Phase 4 if the "generalized attributed-value" idea in Section 3 is pursued.

## 5. Data gaps vs. application gaps

**DATA GAP** (the dataset itself doesn't have enough — no amount of UI work fixes this):
- Only one Assessment and one Recommendation exist in total (by Phase 1.5A's explicit, deliberate scope) — the Landscape's "What deserves attention" section will show exactly one of each until real analyst throughput exists. Not a bug; an honest limitation carried into the UI rather than hidden.
- 3 of 40 real varieties have ≤1 linked evidence record (surfaced explicitly in the Landscape's "Thin coverage" callout rather than papered over).
- Patent-to-variety linkage is populated for only 12 of 42 varieties (`attributes.patent_number` set) — the rest have no patent identifier recorded at all, independent of the matching-mechanism limitation in Section 2.
- 16 of 42 varieties have no `attributes.traits` entries — no trait provenance to show, regardless of UI capability.
- **Five entities and three evidence records in the live dataset are explicitly self-described as fictional V1 seed/demo data** (`company-example-genetics`, `company-example-nursery`, `retailer-example-market`, `variety-example-blue`, `variety-example-red`, plus `ev-sample-patent-published`, `ev-sample-retail-placement`, `ev-sample-variety-launch`) — each literally contains the word "Fictional" in its own `description` field — but are stored in the same `data/entities/`/`data/evidence/` folders as real intelligence with **no structural field distinguishing them**. The Landscape had to exclude them via a hard-coded id list (`SEED_FIXTURE_ENTITY_IDS`/`SEED_FIXTURE_EVIDENCE_IDS` in `app/main.py`) to honor this task's "do not invent placeholder intelligence" instruction. This is real technical debt: a future import, a new report, or a repository-level query has no way to exclude these short of hard-coding the same id list again. **Recommendation for Phase 2/3**: either move these to a dedicated fixtures/test-data location outside `data/`, or add a real `is_seed_data: true` (or similar) field so any consumer can filter them structurally.

**APPLICATION GAP** (the UI simply didn't do this before; now fixed):
- Before this task, no view synthesized cross-object relationships at all. `entity.html` showed only Facts and linked Evidence — nothing about Signals, Assessments, Recommendations, or an entity's relationships to *other* entities. Fixed generically for every entity type (Section 1).
- No Landscape/rollup view of any kind existed. Fixed by BL-026.
- The Company page had no "portfolio" grouping distinct from the flat chronological activity feed — named explicitly as a known gap in this task's own brief (`CURRENT-STATE-AUDIT.md` Workflow B) and closed here via the generic "Portfolio & network" section.
- Trait data existed in `attributes.traits[]` since import but nothing rendered it, so trait provenance (claim vs. measurement) was invisible in the UI even though the data was structured and present. Closed by BL-028's trait-profile table.

## 6. UX findings

- **Strongest small win**: the variety trait-profile table's "Source of claim" column, reusing the existing `badge-claim`/`badge-fact` vocabulary. It turns "is this a real measurement or a marketing claim?" — previously answerable only by reading raw JSON — into a glance-able badge, using components that already existed.
- **Existing components generalized without modification**: `.trust-summary`, `.entity-links`, `.fact-list`, `.feed`/`.feed-compact` all dropped into the Landscape and enhanced entity pages as-is. No new component vocabulary was needed beyond a handful of Landscape-specific layout classes (`.landscape-section`, `.coverage-grid`, `.geo-table`) and a `.trait-table`.
- **Wide tables need a real responsive answer.** The competitive-field and variety-rollup tables (7-8 columns) needed `overflow-x:auto` wrapping even at desktop widths and would need real column-priority/collapse behavior on narrower viewports — flagged, not solved; acceptable for a prototype, not for Phase 4's productionized version.
- **Counts-that-could-mislead were designed against directly**, not discovered as a problem: the competitive field and variety landscape are alphabetical, not sorted by any count, specifically to avoid a table order implying a ranking. A future productionized version will face real user pressure to add "sort by patents" or similar — that affordance needs its own care not to reintroduce an implied ranking through the back door.
- **The Assessment/Recommendation domain-scope gap (Section 4) has a UX consequence, not just a data-model one**: the Landscape's entity-intersection approximation means a future Assessment about an unrelated berry that happens to name a shared entity (a company active in both blueberry and raspberry, say) could appear on the wrong Landscape. Not currently possible (no such data exists), but worth fixing structurally before Phase 4 productionizes this for a second berry.
- **Disputed-status visibility, called out as a live V1 gap in `03-DOMAIN-MODEL.md`** ("`disputed` status must carry real visual weight, not plain-text-only rendering"), got a real fix as a side effect of this task's badge work: disputed Facts and Relationships now render a `badge-counterevidence`-styled "DISPUTED" badge inline wherever they appear (entity pages, Assessment/Recommendation/Signal detail pages), not just in status text.

## 7. Scope selector — what a real implementation would require

This phase renders `Berries / Blueberry / Global` as a static label on the Landscape header, per explicit instruction not to build the full mechanism yet. A real Domain/Market/Geography scope selector would require:
- A `Workspace`/`Domain` object actually existing (`03-DOMAIN-MODEL.md` — currently planning-only, Phase 3+).
- Every core object's queries re-scoped by active Domain, not by ad hoc `berry_id in entity.berry_ids` filtering (which only works because this deployment has exactly one populated berry today).
- A resolved answer to the Assessment/Recommendation domain-scope gap (Section 4) — the scope selector can't be trusted for those two object types until it exists.
- UI state (probably a dropdown or breadcrumb-style selector) that changes the route/query parameters for every synthesis view, not just a label.

## 8. Phase 2 implications — concrete repository-interface requirements

Derived directly from what this prototype needed (Section 2), not guessed in advance:

1. `objects_referencing_entity(entity_id, types=[...])` — one call replacing the five separate per-type full-scan helpers (`signals_for_entity`, `assessments_for_entity`, `recommendations_for_entity`, `facts_for_entity`, `relationships_for_entity`).
2. `entities_by_type(entity_type, domain_scope=...)` — replacing the repeated full-scan-and-filter pattern in `landscape_entities()` and elsewhere.
3. `relationships_for_entity_grouped(entity_id, resolve_other_side=True)` — the join-and-group operation `grouped_relationships_for_entity()` does in application code today.
4. A resolved design for domain/berry scope on Assessment and Recommendation — either a real schema field or a repository-level computed-membership view — replacing the transitive entity-intersection workaround before a second berry or domain makes that approximation unsafe.
5. `evidence_filtered_by_relevance(cited_by=[...])` — evidence selection driven by "something else already judged this relevant," the pattern behind "Recent meaningful movement," rather than requiring callers to assemble an id whitelist by hand.
6. `geography_rollup(domain_scope, region_map)` — a first-class aggregate query (geographies/companies/evidence per region), computed once and cacheable, not recomputed from three separate full scans on every Landscape request.
7. `distribution(field, scoped_to=entity_ids)` — a generic confidence/status/dispute-count aggregate, replacing the ad hoc `Counter()` calls in `landscape_evidence_coverage()`.
8. A real per-request compute-once cache at the repository layer. Today's only caching is `load_json_files()`'s file-mtime-based cache (correct, but coarse — it caches *file contents*, not *query results*); several Landscape helpers redundantly call `all_facts()`/`all_relationships()`/`published_evidence()` multiple times within a single request. Once Phase 2 introduces a real interface boundary, that's the natural place to attach request-scoped memoization.
9. A structural way to exclude non-production fixture/seed data (Section 5) from any query — today this requires every consumer to know and hard-code the same exclusion list this prototype introduced.
